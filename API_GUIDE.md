# Docs API Guide

The complete guide to writing and managing documentation through the docs API.
The [README](README.md) gets the stack running; this is the reference for
everyone (and every agent) who writes to it. The seed script publishes this
guide into your own docs site as `guides/docs-api.md`, so it's self-hosting.

Throughout, `$API` is your docs-api base URL (default `http://localhost:8010`)
and `$KEY` is your `DOCS_API_KEY`.

## Quickstart: writing a page

A page is created or updated with one call — no helper script, no SSH:

```
curl -X PUT $API/api/docs/pages/services/my-thing.md \
  -H "X-API-Key: $KEY" \
  -H "If-Match: *" \
  -H "Content-Type: application/json" \
  -d '{
        "title": "My Thing",
        "nav_path": "Services/My Thing",
        "content": "# My Thing\n\n...markdown body..."
      }'
```

That's the whole write path — the site rebuild is automatic (~10 s).
Everything below is detail: safe concurrency, the large-content workflow,
move/archive/redirect, the nav-section guard, and the lifecycle model.

## Core model — the dimensions of a page

A page has three independent properties. Do not collapse them:

| Dimension | Field | Meaning |
|-----------|-------|---------|
| Identity | `path` | The URL (`services/my-thing.md` → `/services/my-thing/`). Changed only by `pages/move`. |
| Presentation | `nav_path` | Where it sits in the sidebar (`Services/My Thing`). Changed freely; never affects the URL. |
| Lifecycle | in the Markdown body | What kind of document it is (see below). Lives in the content, not the database. |

- Changing `nav_path` never changes the URL; `pages/move` never changes the lifecycle.
- `path` and `nav_path` are API/DB concerns; lifecycle lives in the Markdown
  so exports stay self-describing.

**Deploys are never dropped:** every write signals a persistent deploy worker
that coalesces bursts into a single rebuild from the latest database state.

## Authentication

All endpoints except `GET /api/health` require an `X-API-Key` header.

`GET /api/agent-config` returns the key *to already-authenticated callers* in
this package's default configuration (`DOCS_AGENT_CONFIG_REQUIRE_KEY=true`) —
it's a config echo, useful for verifying a client's setup. Only deployments
with a real network boundary (LAN-only reverse-proxy middleware) should relax
that flag to get IMDS-style anonymous bootstrap. See SECURITY.md.

## Path and content constraints

- `path` must match `^[a-z0-9/_-]+\.md$` (lowercase, no dots except `.md`).
- Content must begin with a Markdown H1 (`# Title`) — a page starting with
  anything else (including an HTML comment) is rejected with 422. Put
  metadata comments *after* the H1.
- Max content size: 1 MB.
- When you GET a page to edit it, strip the leading
  `<!-- Generated by ccm-docs -->` stamp before re-writing — the renderer
  re-adds it.

## Concurrency — If-Match

Creating a new page needs no `If-Match`. Updating an existing page requires it,
in one of two modes:

- `If-Match: "<revision>"` — **optimistic lock**: the UUID from the GET
  response (also in the `ETag` header). Returns **412** if someone wrote
  first; re-fetch and retry.
- `If-Match: *` — **upsert**: overwrite the current latest in one call, no
  prior GET. The read-modify-write happens under a row lock, so it's
  race-free — this is explicit opt-in last-writer-wins.

Omitting the header on an update returns **428** with instructions.

### Recommended workflow for large content

Write the payload via a file to avoid shell-escaping pain:

```
python3 -c "
import json
print(json.dumps({
    'title'     : 'My Service',
    'nav_path'  : 'Services/My Service',
    'content'   : open('/tmp/content.md').read(),
    'updated_by': 'your-name-or-agent',
}))" > /tmp/payload.json

curl -sf -X PUT $API/api/docs/pages/services/my-service.md \
  -H "X-API-Key: $KEY" -H "If-Match: *" \
  -H "Content-Type: application/json" \
  -d @/tmp/payload.json | jq '{path, version, action}'
```

## nav_path conventions and the nav-section guard

`nav_path` is `Section/Title` or `Section/Subsection/Title`. Two rules the
API enforces at write time (so a bad write can never break the next deploy):

1. **Leaf/section conflict** — a name cannot be both a page title and a
   section. If `Products/Widget API` exists as a page, you cannot add
   `Products/Widget API/Errors`; give the parent an explicit sub-title first
   (`Products/Widget API/Overview`). Conflicting writes return 422 with the
   exact collision named.
2. **Nav-section guard** — the most common mis-file is deriving the sidebar
   section from the URL path (filing `services/foo.md` under `Services/…`
   when its path-siblings all live under `Products/…`). The API compares
   your `nav_path` against the strict-majority section of the page's
   path-siblings: a clear path-derived divergence is **blocked (422)**;
   other divergences get a non-blocking `warnings` array on the response.
   If the divergence is deliberate, resend with `X-Nav-Override: true` —
   the write succeeds and the override is logged.

Use `GET /api/docs/nav` before writing to see existing section names —
case and whitespace matter; reuse them verbatim.

## Endpoint reference

Read:

```
GET  /api/docs/pages                       list (?status=active|inactive|archived|all)
GET  /api/docs/pages/{path}                one page + ETag (?include_archived=true)
GET  /api/docs/pages/{path}/history        version history
GET  /api/docs/pages/{path}/versions/{rev} one historical version
GET  /api/docs/nav                         rendered nav tree + conflicts
GET  /api/docs/nav/sections                top-level section ordering
GET  /api/docs/search?q=…                  full-text search
```

Write:

```
PUT    /api/docs/pages/{path}              create / update (If-Match rules above)
POST   /api/docs/pages/{path}/archive      soft delete (If-Match required)
POST   /api/docs/pages/{path}/restore      restore an archived page (If-Match from
                                           GET ?include_archived=true)
DELETE /api/docs/pages/{path}              hard delete — destroys the page AND its
                                           history; almost always use archive instead
POST   /api/docs/pages/{path}/rollback/{rev}  restore a historical version as new current
POST   /api/docs/pages/move                relocate a URL (atomic, optional redirect)
POST   /api/docs/pages/{path}/add-redirect idempotent redirect repair
POST   /api/docs/nav/reparent              bulk sidebar move (URLs unchanged)
PUT    /api/docs/nav/sections              set top-level section order
```

Operate:

```
POST /api/docs/deploy[?dry_run=true]       manual rebuild (writes auto-deploy)
POST /api/docs/render                      dry-run with per-file hashes + checksum
GET  /api/docs/drift                       DB-vs-disk comparison
GET  /api/docs/lint                        content lint findings
GET  /api/docs/lifecycle/check             lifecycle validation (see below)
GET  /api/docs/redirects/reconcile         redirect health check
GET  /metrics                              Prometheus metrics
```

`/docs` on the API serves the interactive OpenAPI UI with full schemas.

## Moving, archiving, deleting

- **Reorganize the sidebar** → `POST /api/docs/nav/reparent`
  (`{"from_prefix": "Services/Old", "to_prefix": "Network/Old"}`) — every
  matching page moves in one transaction, URLs unchanged.
- **Change a URL** → `POST /api/docs/pages/move`
  (`{"from_path": …, "to_path": …, "create_redirect": true}`) — archives the
  source, creates the destination, and appends a `redirect_maps` entry to
  `mkdocs.yml` so old links keep resolving. If the response says
  `repair_required: true`, the DB move committed but the redirect write
  failed — fix with `add-redirect`, don't re-move.
- **Remove a page** → `POST …/archive`. It leaves the live site but keeps
  full history; restore any time. `DELETE` is for pages whose entire history
  must be destroyed — there is no undo.
- Redirect entries are permanent until manually removed; use
  `create_redirect: false` for throwaway test moves, and run
  `GET /api/docs/redirects/reconcile` after bulk moves.
- The API does not rewrite inbound links. After a move, update referring
  pages — and never do corpus-wide basename replaces: `](monitoring.md)`
  resolves relative to *each linking page's directory*, so the same bare
  basename can point at different pages.

## The lifecycle model

Every page should declare what kind of document it is, immediately after
the H1 — a human line plus a machine token:

```
# My Document

**Lifecycle:** REFERENCE
<!-- lifecycle: REFERENCE -->
```

The six states: `OPERATION` (runbooks), `ACTIVE` / `PAUSED` / `BACKLOG`
(work-tracking docs by state), `REFERENCE` (enduring architecture/design),
`ARCHIVED` (historical record — how we got here, no longer what to believe).

Classify by the document's *purpose*, not its title and not the state of the
system it describes: an architecture doc for a half-built system is still
REFERENCE. One document, one lifecycle — if part of a page has a different
lifecycle, that part wants its own page. Keep one canonical document per
concern per lifecycle (a second backlog page for the same subsystem is
fragmentation, not thoroughness).

`GET /api/docs/lifecycle/check` validates the corpus: ERROR when field and
token are missing or disagree, WARNING for unknown states. Adoption can be
incremental — an unclassified page is "not yet classified", not broken.
(Note: `Lifecycle: ARCHIVED` is a declaration on a *live* page; `POST
…/archive` removes a page from the site. Different things.)

## Before you create a new page

Fragmentation is the slow failure mode of every docs corpus. Four questions
first:

1. Should this content extend an existing page instead?
2. What lifecycle will it have? (Pick before writing — it shapes the writing.)
3. Does a document with this lifecycle already exist for this concern?
4. If it's REFERENCE — should the knowledge accrete into an existing
   REFERENCE page rather than start a fresh one?

## Rendering gotchas

- **Single-line code blocks**: Material's copy button sits inside the code
  block's box; a one-line block gives it no height and long lines push it
  off-screen. Write copy-paste blocks multi-line.
- **Mermaid**: fenced ` ```mermaid ` blocks render as diagrams
  (see `mkdocs/overrides/main.html` for how, and for vendoring the JS
  locally on offline networks).
- Generated views beat hand-maintained indexes: if you build a section index,
  generate it from the lifecycle tokens rather than curating a table of
  contents that rots.

## Architecture

```
Agent / script / MCP client
  │  PUT /api/docs/pages/{path} …
  ▼
docs-api (FastAPI)
  │  INSERT/UPDATE docs.pages       (PostgreSQL = source of truth)
  │  _schedule_deploy()             (event signal, bursts coalesce)
  ▼
deploy worker (persistent daemon)
  ├── render pages → mkdocs/docs/   (with generator stamp + Last-updated)
  ├── write mkdocs.nav.yml          (generated nav child-config; INHERITs mkdocs.yml)
  ├── mkdocs build → staging dir
  └── rsync --checksum → mkdocs/site/   (atomic per file — no 404 window)
  ▼
nginx (docs-web) → readers            (+ /raw/ markdown sources)
  ▼
docs-mcp reindexes on the /reindex webhook
```

The filesystem is derived state — never edit rendered `.md` files or
`mkdocs.nav.yml` directly; the next deploy overwrites them and
`GET /api/docs/drift` reports the interference. Hand-maintained config
(theme, plugins) lives in `mkdocs/mkdocs.yml`; the nav and `redirect_maps`
block are API-owned.
